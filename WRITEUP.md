# Opportunity Engine — Submission Writeup

Team: Niranjan Iyer, Swarali Patil · Bharat Builds Tour — First Commit (WeMakeDevs × AWS), Sept 17–20, 2026

## Problem

A small business owner already has three sources of truth about where to grow: their own
customers' feedback, their competitors' public reviews, and the wider market conversation. No
one has time to read all three, cross-reference them, and turn the overlap into something
actionable — so most businesses either pay for a market-research report that's stale on
arrival, or ask a chatbot, which researches confidently but can't prove any of it.

**Opportunity Engine finds where a competitor's customers are unhappy about something the
business is already good at, backs that claim with evidence code can verify, estimates what
it's worth against the owner's stated goal, and hands the owner an execution pack they
control.** The product bet is a specific one: *agents discover, code verifies, humans decide*.
Research agents are structurally limited to emitting `signals[]` — the `opportunities[]` field
doesn't exist in their output schema, not just unused by convention — so an LLM never gets to
assert "this is an opportunity" on its own authority. A deterministic Evidence Check (does the
quote exist, does it actually support the claim, is it fresh) and Quality Gate (14 checks, a
rule-based priority tier, no composite score) decide what's allowed into the inbox. The
Opportunity Detail screen makes that verification step visible on screen, not just claimed in a
pitch — a live Evidence Check diagram replays exactly why each claim was accepted or rejected.

## Build

Flagship business: **PulseStack**, a simulated B2B SaaS selling lightweight error/uptime
monitoring, competing against real named tools (Sentry, Datadog, etc.). PulseStack's own
feedback (support tickets, churn notes, survey responses) is generated by a seeded simulator
with planted truths and red herrings, so the pipeline's output is measurable, not just
admirable — the agents' IAM role never sees the truth manifest. Every competitor claim is
sourced from real, live-retrieved public reviews/discussions, never invented.

Pipeline: Market, Feedback and Competitor research agents each emit `signals[]` only → a
Synthesis agent proposes `candidate_opportunities[]` with a stated mechanism (why the pain and
the strength combine into something actionable, not a coincidence) → Evidence Check → Quality
Gate + Ranker → DynamoDB. A separate Action Agent turns a gate-passed opportunity into an
execution pack (offer, proposal, outreach drafts), with an `outreach_policy` enforced in both
the prompt and a post-generation code check so a draft can't cite a strength the business
hasn't actually verified.

Five screens: business profile, live investigation (streaming research lanes), the opportunity
inbox (including "ideas we rejected," the signature moment), opportunity detail with the
Evidence Check diagram, and the execution pack. Every external data source (Tavily, GitHub, HN,
App Store, Product Hunt, and each evidence fetch) carries a Live → Cached → Demo Fixture label
in the response and the UI, and a substitution is always labelled, never silent — including once,
on Day 3, when the deployed frontend was found serving `DEMO FIXTURE` on every screen because an
env var had never been set on the live Amplify app; the fallback had been working exactly as
designed the whole time, just unnoticed until someone checked the actual public URL instead of
local dev.

## AWS integration

Deployed and running on AWS, not just diagrammed:

| Service | Role |
|---|---|
| **Amplify Hosting** | Frontend, git-connected to `main`, auto-builds on push |
| **API Gateway** | REST surface for all five screens |
| **Lambda** | 13 functions — every read/write handler, plus the Evidence Level 2/3 fallback |
| **DynamoDB** | Single table + GSI1, all nine core entities (businesses, runs, signals, opportunities, claims, evidence, targets, execution packs, source documents) |
| **S3** | Evidence cache bucket backing the Live → Cached → Demo Fixture ladder |
| **Step Functions** | Orchestrator (currently the Day 1 skeleton — one Task state proving Lambda invocation; the full five-stage research pipeline that produced the one real live opportunity runs today via a local script, not yet re-wired into the state machine — shown honestly on the architecture diagram rather than left off it) |
| **SSM Parameter Store** | Product Hunt developer token |

**Bedrock, honestly.** The architecture was designed around Amazon Bedrock via the Strands
Agents SDK (Haiku 4.5 for research, Sonnet 4.6 for synthesis), and IAM access to both models
shows "Access granted" — but real-time inference quota came back **0 req/min on every AWS
account we tried**, confirmed dead on Day 3. Rather than block the whole pipeline on a support
ticket, every agent's model calls were migrated to OpenCode Go (`deepseek-v4.1-flash`) behind
the same Strands-agent interface, so the reasoning architecture (agents propose, code verifies)
never changed — only which model answers the call. That gap, and the fix, are on the
architecture diagram (`docs/architecture-diagram.md`) and in `LEARNING.md` rather than smoothed
over, for the same reason the product never silently substitutes a data source: a stale diagram
that hides the real system isn't a diagram, it's a claim.

## AI tools used

- **Claude Code** (Anthropic) — the primary tool used to write essentially all backend, frontend,
  infrastructure and test code across the four days, driven from a committed task list
  (`tasks/plan.md`, `tasks/todo.md`) and repo-level instructions (`CLAUDE.md`, `AGENTS.md`) so
  every session picked up the same contract and guardrails rather than re-deriving them.
- **OpenCode Go** (`deepseek-v4.1-flash`) — not a coding tool but disclosed for completeness: this
  is the model that actually powers every research/synthesis/action agent call in the deployed
  product, substituting for the originally-planned Amazon Bedrock calls for the quota reason
  above.
- No other AI writing/design tools were used to produce submitted code or copy.

All code was written during the event window (17–20 Sept 2026); no pre-existing project was
adapted. Third-party libraries used are standard open-source dependencies, listed with licences
in `CREDITS.md` — no other party's original code was copied into this repository.
